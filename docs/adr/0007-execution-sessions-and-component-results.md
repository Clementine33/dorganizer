# 0007 执行会话：编码池、提交顺序与组件结果行

Date: 2026-09-22

Status: Draft

执行会话全局串行（同一时刻只有一个），会话内部按冻结单元依次走：每个单元生成全部输出、校验、提交，然后移除过时音频，再开始下一个。每次编码都是单线程的 ffmpeg 进程，于是四核机器上有三个核闲着，一个大文件也会挡住后面所有文件夹。参考负载实测（2.67 GiB WAV，单个组件 6 个文件，目标 mp3 320 kbps）：

| 策略 | 桌面 | NAS |
|---|---|---|
| 串行 | 100.8 s（1.10 核） | 149.1 s（1.14 核） |
| 2 个编码 worker | 53.5 s（1.88x） | 83.1 s（1.79x） |
| 4 个编码 worker | 46.0 s（2.19x） | 59.6 s（2.50x） |
| SSD staging | 129.0 s（0.78x） | 未运行 |

两种环境下磁盘占用都没超过 9%，4 个 worker 时单文件编码膨胀 15–25%；剩余上限来自批次里最大的那个文件（单文件编码无法再拆分）。测量用的两个工具（`cmd/io-bench`、`scripts/io-bench-nas.py`）是本地工具，不入库。

## 1 会话全局串行，会话内共享一个编码池

- 同一时刻只有一个执行会话，因此两条记录不会写重叠的根，扫描也不会与执行重叠。
- 会话内部由一个共享的编码池（N 个 worker）跨组件与成员文件夹领取文件任务；工作单元是一个冻结的编码任务（编码 → 探测 → 完整解码校验）。
- 池按冻结顺序填充，因此靠前的组件先编码。投递在有界队列上并可响应取消；组件在它的任何任务被投递前已登记为受管单元；取消后 worker 排空退出，未开始的任务仍完成记账，任何发送都不会阻塞停止路径。
- 投递恰好结束一次（协调者在最后一个单元之后或拆除开始时关闭队列），worker 排空后才退出，因此等待它们总会终止。
- 空执行不启动池，沿用原有的完成/取消规则。

## 2 组件准备窗口 W = N

- 整个会话最多有 N 个组件处于已准备但未提交状态；一个已完成编码但尚未提交的组件仍占着自己的槽位。
- 窗口限定的是：预检在文件真正编码前能有多旧、同时存在的暂存文件规模、以及一次失败会丢弃多少工作。它不限定单个组件的输出数量、队列长度，也不限定组件等待提交的顺序——慢的头组件会一直占着槽位，后面的组件在窗口满时进不来，worker 可以闲置。这一闲置是选择简单窗口的代价。
- 成员文件夹不是批处理边界：窗口与池都跨它们自由流动。

## 3 单协调者按冻结顺序提交

- 头组件的编码全部返回后，协调者重新探测每个暂存输出（沿用已有的校验，不做重复完整解码），用同目录 rename 提交、移除过时音频、并持久化进度与原委。
- 提交、移除、回收副本、库存同步与持久化因此都是单线程且无竞态的。
- 每个停止信号（同侪失败与用户取消一样）都在**提交操作之间**生效：已开始的 rename 或移除会完成，因此回收副本不会被毁在半途。不声称更强保证：I/O 失败仍可能留下部分提交的组件，这类组件报告它自己的部分事实（已提交/已移除/剩余/回收），而不是被降级为 pending。
- 进度在头组件已知时立刻写下——每次提交顺序迭代开始时，在准备或投递可能阻塞之前；每次边界发布下一个头组件及其提交的结果，因此只有第一次迭代需要单独写。

## 4 失败与取消：fail-fast，不回滚

- 一个拆除序列服务所有停止：编码失败、准备或提交失败、用户取消。它们共用一个并发安全的停止入口，在取消共享上下文之前记录第一个真实错误及其单元索引（上下文取消与被取消的组件从不是真实错误）。
- 编码任务与提交观察同一上下文：某个 worker 的失败会在下一个操作边界停住同侪的提交，不必等协调者收到通知。准入停止、队列恰好关闭一次、等待每个 worker 与其编码子进程退出，然后才收尾未完成组件并持久化终态。
- 准备失败归因于正在准备的单元（即使还没有已准备的单元也保留它的索引），绝不归因于头组件。只有任务失败的组件标记为失败；已提交的组件永不回滚；一个串行执行本会提交的无辜组件保持 pending——这是 fail-fast 的代价，也是相对串行执行唯一刻意的行为变化。它在组件条目上保留未运行的操作范围；清理无法移除的回收路径也记录在那里。

## 5 组件结果行与读取分流

- **每个组件的结果是它自己的一行**（`execution_component_results`，键为 `(execution_id, component_index)`），在一个短事务中随会话计数与位置一起写；编码与文件操作仍在该事务之外。已发生的事实都落盘，且没有任何写会重写它们。
- 会话行保留状态：状态、计数、当前位置、取消标志、错误。冻结的组件清单不重复存储——它就是会话的冻结工作清单，装配时把结果并上去。**没有整份报告列**：曾把整份报告写在自己的行上并在每个组件边界重写两次，`N` 个组件让写入量按 O(N²) 增长（1000 组件实测：整份重写 4.98 s / 420 MB WAL，逐组件结果行 0.19 s / 13 MB）。
- 计数是推导的，不是累加的：边界事务从已存结果重算已完成组件与操作数，因此重放的写天然幂等，未运行的组件无法被计数。
- 没有结果行的组件就是 pending：中断的会话仍列出全部组件，结果为空。拆除时把未运行的操作与被保留的残留写成那些组件的结果行；这些行写失败只记日志——它们描述的磁盘状态不受影响，会话照常结束。
- 读取按用途分流：事件流轮询只含控制信息（状态、取消标志、计数、位置）的投影；取消看门狗仍读会话行。明细读取把冻结清单与已记录结果装配起来，可选按组件索引分页；SSE 快照就是这份装配结果，随后每个组件的结果落地时单独推送它的条目，终态事件在其后。
- 结果写持续失败会停止会话：只重试写本身（有界次数，绝不重试编码或已完成的提交），然后报为会话失败。

## 6 无跨盘 staging，池大小是构造参数

- 不做跨盘 staging：输出以 `*.tmp.<token>` 暂存在目标旁边，用同文件系统的 rename 提交，执行器不跨盘移动。
- 池大小是构造参数：`0` 表示自动（`min(4, runtime.NumCPU())`），窗口 `W = N`；将来可以由用户设置覆盖，本期不暴露在草稿或 API 里。

## 替代方案权衡

- 拒绝串行执行：四核机器只用了约 1.1 个核，编码池在同一负载上拿到 1.79–2.50x。
- 拒绝跨盘（SSD）staging：实测 0.78x，它把编码本来与 CPU 重叠的读取串行化了，而两种环境的瓶颈都不是磁盘。
- 拒绝每个成员文件夹一个池、或按文件夹分批：成员文件夹不是工作负载的自然边界，池与窗口都应当跨它们流动。
- 拒绝「无界并发」与「每个组件并行提交」：提交、移除、回收副本与库存同步必须单线程，否则回收副本与库存可能被并发写坏。
- 拒绝「失败即回滚已提交的组件」：回滚意味着再次写盘，而失败时的磁盘状态本就未知；宁可如实报告部分事实。
- 拒绝「失败自动重试编码或提交」：重试可能在半完成状态上继续，且结果写失败不等于编码失败。恢复路径是刷新输入后生成新的计划。
- 拒绝把整份报告写在一行：O(N²) 的序列化与 WAL 体积是实测的，逐组件结果行同时让读取按用途分流成为可能。
- 拒绝让取消看门狗读整行：看门狗只需要取消标志与计数，读整行会把每次轮询都变成全量装配（当前实现仍读会话行，这是已知的、可收敛的差异）。
