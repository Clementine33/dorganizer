# 0008 数据库自清理与会话留存

Date: 2026-09-22

Status: Accepted

`cache.db` 是应用唯一打开的 SQLite 文件。它的两个属性与留存策略的假设逐渐脱节：

- 留存只在进程启动时跑一次。长驻进程之后什么都不删，文件随应用创建的会话增长。
- 删除行把页放回 freelist，之后的写会复用，但文件本身从不缩小。freelist 因此不可见：文件大小是一条没有任何策略会降低的高水位线。

审计删除条件时发现两个必须先修的缺陷：扫描删除按 `COALESCE(finished_at, started_at)` 判断且没有状态过滤，因此运行超过 7 天窗口的扫描会在自己进程底下被删；进程在扫描中途被杀会留下 `queued`/`running`/`merging` 行，而 `HasActiveScanForRoot` 把这类状态当作活动扫描，于是它会无限期拒绝针对该根的规划与执行。启动时跑一次使第一个缺陷难以触发，每天跑就不是了。

## 1 只删终态行，启动时收尾死进程留下的行

- 扫描会话可删的条件是：状态为终态（`completed`、`failed`、`canceled`、`interrupted`）且其终态时间早于截止点。`queued`/`running`/`merging` 行属于正在飞行中的扫描，或属于进程已死的那次——数据库不是判定者，因此它绝不按时间删除。
- 它改为被收尾：启动时，在 dispatcher 启动之前，`InterruptStaleScanSessions` 把非终态扫描行标记为 `interrupted` 并写上 `finished_at`。这与 `InterruptStaleGenerations`、`InterruptStaleExecutions` 一致，并且一举两得：该行不再拒绝它的根，它的留存时钟从被收尾的那一刻开始计，而不是从很久以前的 `started_at` 起算（崩溃不会在被发现的一瞬间就被删掉）。
- 规划会话继续以 `finished_at IS NOT NULL` 作为终态判断。

## 2 维护是进程内的空闲批处理

- 每个进程一个循环，随进程启动、随停止 HTTP 服务器的同一个上下文停止；没有调度器、没有守护进程、没有端点。启动那一遍在开始服务之前跑完（此时进程里没有别的工作），之后循环按 tick 的节奏接管：刚启动的进程不会用一次没人要的清理拒掉它的第一个客户端。
- 空闲不是循环能询问的属性，所以它采用直接文件管理的那套办法：申请进程级准入槽位（0002），让答案可以是否决。持有该槽位就是「空闲」成立的原因：持有期间到达的扫描、文件操作或会话入队会被拒绝而不是并行启动，反过来先到的任务也会否决这次维护。一次检查覆盖扫描、规划与执行，正是它复用该槽位而不是各自判断的原因。
- 槽位按小批次持有、批次之间释放，因为拒绝是用户要处理的回答。每轮还有预算（批次，然后页）；用尽就停止并在下一个 tick 继续，被拒绝时同样如此。只有完整做完工作的一轮才被推迟一整个间隔。循环不承诺持有时长——批次由行数与页数界定，日志行携带耗时。

## 3 只有以增量 auto-vacuum 创建的库才能归还页

- `PRAGMA auto_vacuum` 在文件创建时固定：在第一张表存在之前设置会写进文件头，之后再设置是静默的空操作，只有完整 `VACUUM` 才能改变。
- 连接参数请求增量 auto-vacuum，新建的库都会带上，已有的库不变；读回该模式以决定是否值得尝试回收。
- 因此已有数据库完全照旧工作——清理继续跑，回收跳过——日志说明一次，并指出唯一能改变它的动作（把 `ONSEI_DATA_DIR` 指向新目录）。
- schema 生成（marker 行）不匹配的数据库在打开时**被拒绝**：不迁移、不清空、不自动重置，错误信息给出路径与出路。本次迭代一律用新数据库验证，旧数据目录继续可用是因为结构未变，而不是因为迁移。
- 刻意不做：用一次性完整 `VACUUM` 转换文件（需要与数据库等大的工作空间，并在运行期间阻塞一切）；也刻意不通过提升 schema 版本来强制重置（schema 版本留给结构变化，不用于家务）。

## 4 回收是推迟的，不是争抢的

`PRAGMA incremental_vacuum` 把空闲页从文件尾部移走，在 WAL 模式下发生的截断其实在能拷完整份日志的 checkpoint 上，而不是提交时。因此每轮以一次 PASSIVE checkpoint 结束：它从不等待读者，不完整的 checkpoint 是正常结果，下一轮会继续改进。不用 `TRUNCATE` 重试——它会在持有准入槽位时等待同一批读者，反而阻塞该槽位要保护的任务。

## 5 SQLite 驱动与事务不变式

- 内嵌的 SQLite 必须 ≥ 3.51.3：3.51.2 位于 WAL 重置导致损坏的缺陷范围内（该缺陷需要并发写者与 checkpoint，正是本应用已有的形态，而这个决定又增加了一次 checkpoint）。驱动升级作为独立提交先行落地。
- 该升级不是中性的：3.51.3 起，SQLite 会拒绝延迟事务的「快照升级」（此前静默应用并丢掉并发提交）。本应用的每条写路径都先读后写（找排队会话、载入冻结草稿，然后认领或持久化），延迟事务会输掉这个竞态并拿到 `SQLITE_BUSY_SNAPSHOT`。
- 两个配套改动：读改写事务以 immediate 开始（DSN 上的 `_txlock=immediate`），因此事务在读之前就持有写锁；只读事务保持 deferred（驱动只在事务非只读时应用该模式）。认领失败要重试并报告，而不是当作空队列——在唤醒通道上休眠是缺陷的另一半：认领失败的会话已经排队，因此不会再有入队来唤醒 worker，队列会静默停滞到下一个无关会话到来。

## 替代方案权衡

- 拒绝「启动时跑一次留存」：长驻进程之后什么都不删；改为空闲批次，并保留启动时的收尾（收尾与删除是不同的动作）。
- 拒绝「按时间删除非终态扫描行」：那会在扫描自己的进程底下删掉它；改为启动时收尾。
- 拒绝在 gate 上提供可查询的空闲标志：gate 的拒绝就是答案，单独检查会与它要排除的启动竞态。
- 拒绝为维护建立优先级队列：维护与其他写入争同一个槽位，被推迟一轮不损失什么。
- 拒绝在同一次改动里清理执行结果与暂存行：它们的留存规则是另一个决定，窗口也与幂等窗口不对齐。也拒绝自动压缩（VACUUM）：它回收空闲空间，不决定保留什么，且运行期间阻塞一切。
- 拒绝用 schema 版本强制重置：那是为结构变化准备的杠杆，不是家务工具；已有数据库清理照跑、跳过回收，日志说明一次即可。
- 不承诺数据库文件大小的上界：本决定限定两张会话账本的留存时长并归还它们释放的页；库存、执行结果与暂存行不在这里清理，窗口内的数据仍在增长。
