# 0004 Task 接缝与不透明载荷

Date: 2026-09-22

Status: Accepted

处理记录模型最初围绕转换而建：它的草稿文档、规划器与执行器都长在通用模块里，计划载荷直接命名 policy 与 component 行，存储表也跟着命名。记录承载的是「文件夹上的一类工作」，将来还会有别的工作（例如按抓取到的元数据重命名），因此转换内容必须坐在接缝之后，而不是长在生命周期里。

## 1 通用侧拥有操作生命周期

身份、归属、版本、草稿、计划、规划会话、执行会话、它们彼此的互斥与它们的存储都留在通用 workset 模块中，与具体任务无关。

## 2 Task 拥有接缝之后的业务内容

一个 Task 声明自己的 `kind`、种子草稿、草稿校验与规范化、规划流程（冻结输入 → 计划载荷）、输入事实的健康规则、成员解析、审阅载荷，以及冻结单元的执行。转换是第一个适配器（`internal/tasks/conversion`）；通用模块永不 import 任务包。

## 3 载荷不透明

草稿文档、计划载荷、计划级事实（策略式 blob、标签快照、摘要）与逐单元结果都以「字节 + kind + schema 版本」跨越接缝。通用侧只存储与转发；它只解码为自己需要命名的事实（计数、状态、根事实、进度）。

## 4 错误以同一个信封跨越接缝

Task 返回 workset 的错误类型，因此错误码与详情原样到达 HTTP 层；通用侧不翻译也不重新包装任务错误。

## 5 每个 Task 都要满足的契约点

- **准入**：通用侧拥有所有权、版本、事务与幂等；任务只报告业务原因。
- **schema 版本**：未知的载荷 schema 版本在每个入口都被拒绝，不尝试兼容读取。
- **冻结的会话选项**：规范化一次，并参与幂等请求哈希；执行时客户端不再传会话选项。
- **进度**：在任务自己的单元边界持久化；协作式取消；终态状态永不回退。

## 替代方案权衡

- 拒绝把转换概念留在通用模块：每次新增任务都会牵动生命周期代码，通用侧也永远无法独立测试。
- 拒绝为任务建立插件注册表或动态加载：本期只有一个适配器，注册发生在组合根的一行里，不需要框架。
- 拒绝可读的通用载荷（通用侧理解 policy 与 component）：「通用」会随第一个任务的字段演化，接缝随之失效。
- 拒绝宽松读取未知 schema 版本：计划载荷是冻结事实，宁可拒绝也不猜测它是什么。
- 旧库策略：早期实现遇到不兼容的数据库会直接重置；现在改为拒绝启动并提示换数据目录（见 0008），本次迭代不再保留「重置」这一行为。
