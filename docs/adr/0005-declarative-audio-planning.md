# 0005 声明式音频规划：目标输出与转换模式

Date: 2026-09-22

Status: Draft

用户要的不是「跑一遍瘦身算法」或「按开关生成」，而是**声明每个分类最终应该有哪些音频**，由规划器推导要生成什么、要移除什么。早期接口提供 slim/prune 模式与生成、清理开关，用户得自己拼出想要的最终形态，且无法表达「这个分类不应该有任何受管音频」。

## 1 声明式规划与目标输出

流水线：观测库存 → 分类分区 → 组件 → 变体组 → 期望音频档案 → 决策 → 操作 → 预计库存。

- 每个档案最多一个无损输出（WAV/FLAC）与一个有损输出（MP3/AAC/Opus 及码率）。
- **声明即最终形态**：声明的输出缺失时由合格源生成；档案未声明的输出（包括某个已声明输出所来自的源文件）在那批替换提交后移除。
- 档案可以不声明任何输出，意思是该分类不持有受管音频：其中观测到的每个文件都是过时的。
- 只有观测到的无损音频算合格源：不做有损升级、不做编码→无损、不做有损→有损换码，也不把当前计划预计产出的文件当作观测源。

## 2 分类与组件

- 分类使用规范化后的字面标签，对计划根源相对路径做大小写不敏感匹配（**不是正则输入**）。分区为 `matched`（界面「无音效」）与 `unmatched`（界面「有音效」），标签描述规则匹配，不证明音频真实性。
- 每个根源、每个分区先隔离再发现关联。
- 组件是同一计划根源与同一分区内、共享父目录或音轨词干的音频文件的传递关联；它是阻塞变更的安全边界，也是 strict 模式下维护编码输出一致性的单位。变体组是组件内按词干分组的同一条逻辑音轨。
- 阻塞的组件不产生可执行操作但保留决策供审阅；其他组件仍可执行。非音频文件不参与协调，其移除取决于替换输出是否提交成功。

## 3 转换模式

- `strict`：保留足够的编码通道，或从合格观测无损源重建整条通道；不满足或不安全的组件被阻塞。模式缺失时按 strict 语义处理。
- `available_sources`：在同一最终形态规则下按变体组工作，但一个变体组若无法达到其全部声明输出，则**原样保留**并记为未满足目标：不生成、不清理。替换不了却仍替换，只会让该组比原来更少。歧义与路径冲突仍然阻塞；放宽规划不是不安全转换或删除的许可。
- 未满足目标本身不阻止执行，与阻塞冲突分开披露。

## 4 编码输出的判定与生成记录

一个有损输出由两个入口之一判定为已满足：

1. **自身实测码率已答复目标**。判定按编解码器分别进行：MP3 与 Opus 在目标减去 1 kbps 容差之内即算满足（容差覆盖探测低报）；AAC 落在目标的一个带内——目标不超过 192 kbps 时为 95%，其上为 60%（ffmpeg 原生 AAC 在该点饱和），且不得超过 110%（远高于声明形态的文件与偏低的文件一样会被替换）。码率为 0 从不满足：它不是证据。
2. **生成记录**证明这个文件是本应用为这个目标写下的，且字节仍是当时写下的那些。这是实测无法判断的编解码器的裁决依据：Opus 是 VBR（同一 160k 设置在不同内容上平均 0.01x–1.13x），AAC 会饱和。

两个入口都不接受的文件是**未确认**，绝不默认为合格——实测码率同样不是质量证据，低码率文件重编码到高目标不会找回失去的内容。

## 5 输入事实与指纹

- 每个计划根源记录其身份、库存指纹与条目数，即计划所依据的事实；由 Task 决定如何重算以及什么算「已移动」。
- 指纹使用路径、大小、修改时间与条目数，接受扫描器在保留元数据的改动上的盲点，而不引入音频内容哈希。

## 6 决策与操作

决策是可审阅的结论（保留、删除、转换）及其原因；保留决策不需要任何文件系统改动。操作是由决策推导出的可执行改动。移除取决于替换输出提交成功，因此「先删后建」永远不会发生。

## 替代方案权衡

- 拒绝 slim/prune 模式与用户自编的「转换 + 清理」步骤序列：声明最终形态更容易验证、更容易解释，也避免用户拼出互相矛盾的步骤。
- 拒绝有损升级、编码→无损与有损→有损换码：这些操作不改善内容，只增加副本；256 kbps 的 MP3 也不是 256 kbps AAC 目标的合格源。
- 拒绝「统一按实测码率比较所有编解码器」：Opus 的 VBR 与 AAC 的饱和会让该规则永远重建自己写出的输出；生成记录是对应的答案，而不是放宽容差。
- 拒绝「实测码率即质量证据」的推论：低码率重编码到高目标不会恢复已失去的内容，因此未确认就是未确认。
- 拒绝用音频内容哈希做输入指纹：代价与扫描时间不成比例，元数据指纹在保留元数据的改动上的盲点被接受为已知限制。
- 拒绝把未满足目标当作执行阻塞：它不改变任何文件，用户应当看到它，而不是被它挡住。
